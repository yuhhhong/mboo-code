# 模型信息与上下文用量设计

## 1. 文档定位

本文档是模型能力目录、可用模型匹配、推理深度选项、供应商 usage 采集和上下文用量展示的权威设计。

本文档覆盖：

- 应用启动时加载 models.dev 模型目录和当前供应商模型列表。
- 清洗并缓存模型上下文窗口、输入输出限制和能力字段。
- 只允许使用供应商模型列表与能力目录成功匹配的模型。
- 前端切换模型时加载模型详情并生成推理深度控件。
- 使用供应商实际返回的 usage 展示当前上下文窗口占用。

本文档不设计长期记忆。上下文压缩、Token 预估和摘要已由[《上下文管理与压缩设计》](./上下文管理与压缩设计.md)接管；`limit` 仍只表达模型能力上限，自动压缩触发以该文档的 70% 阈值规则为准。

## 2. 目标

- 模型能力只来自固定的 models.dev 模型目录，不维护本地手工能力配置。
- 当前供应商实际返回的模型 ID 是前端可选模型集合的唯一来源。
- 模型 ID 匹配规则简单、稳定且不依赖供应商别名。
- 项目启动完成后，所有可选模型都必须具有有效能力信息。
- 前端不能手动输入未知模型，后端也不能接受未知模型发起聊天。
- 推理深度选项严格来自 `reasoning_options` 中的 `effort.values`。
- 上下文占用使用供应商实际 usage，不使用字符数或固定比例伪造。
- 工具循环中的每次底层模型响应都能更新用量，历史会话能够恢复最后一次有效用量。

## 3. 非目标

本期不实现：

- 根据 `toolCall` 过滤模型或动态移除工具。
- 根据 `attachment`、`inputModalities` 或 `outputModalities` 控制附件和输入输出界面。
- `toggle` 和 `budget_tokens` 推理控件。
- 根据 `limit.input`、`limit.output` 或 `limit.context` 自动修改请求预算。
- 超限自动重试。会话上下文压缩、摘要和裁剪见[《上下文管理与压缩设计》](./上下文管理与压缩设计.md)。
- 模型目录运行时刷新、定时刷新、磁盘缓存或旧数据降级。
- 根据模型名称、家族或供应商推测缺失的能力字段。

`toolCall`、附件和模态字段在本期只清洗、缓存并通过模型详情接口返回，不参与模型过滤、聊天校验或前端能力控制。

## 4. 当前项目基础

当前项目已经具备：

- `ModelOptionService` 在应用启动时请求一次当前供应商的 `GET {baseUrl}/models`。
- `ConfigController.GET /config/modelList` 通过统一 `R` 返回 `List<String>` 模型 ID。
- 前端通过 `GET /api/model/list` 加载模型选项。
- `ChatReq` 使用 `modelName` 和可空的 `reasoningEffort` 发起聊天。
- `USER_MESSAGE.modelName` 持久化本轮使用的模型 ID。
- LangChain4j `AiServiceResponseReceivedEvent` 能取得每次底层模型调用的 `ChatResponse`、`TokenUsage` 和 `InvocationContext`。
- `ASSISTANT_MESSAGE` 是助手消息的 JSONL 终态快照，`ASSISTANT_MESSAGE_DELTA` 是仅通过 SSE 推送的运行时事件。

需要调整的现状：

1. 供应商模型列表加载失败时当前仍允许项目启动。
2. 前端当前允许手动输入模型。
3. 模型列表当前只缓存 ID，没有上下文窗口和推理能力。
4. `MyChatModelListener` 当前只记录日志，没有将 usage 关联到 session 和 turn。
5. 前端没有模型详情接口、推理选项校验和上下文用量状态。

## 5. 术语

| 术语 | 说明 |
| --- | --- |
| models.dev 目录 | `https://models.dev/api.json` 返回的全量模型能力目录 |
| 供应商模型列表 | 当前 `setting.json` 中 `base_url` 对应的 `GET {baseUrl}/models` 响应 |
| 清洗目录 | 从 models.dev 原始响应中提取并校验后的全量 `modelId -> ModelInfo` 映射 |
| 可用模型 | 同时存在于供应商模型列表和清洗目录中的模型 |
| 底层模型调用 | LangChain4j 在一次 AI Service 调用中实际向供应商发起的一次请求；工具循环可能产生多次 |
| 当前上下文用量 | 最后一次成功底层模型调用的实际 Token 总数相对于 `limit.context` 的占比 |

## 6. 总体流程

### 6.1 启动流程

```text
读取 setting.json
  -> 校验 api_key 和 base_url
  -> 请求一次 models.dev 模型目录
  -> 清洗为按原始顺序排列的全量模型能力映射
  -> 请求一次当前供应商 /models
  -> 按 /models.data 原始顺序先做 modelId 精确匹配，失败后做归一化 name 匹配
  -> 生成不可变的可用模型列表和详情映射
  -> Spring 应用继续完成启动
```

任一步骤失败都抛出启动异常，不能只记录警告后继续运行。

### 6.2 前端模型流程

```text
加载原模型列表接口
  -> 选择或恢复 modelId
  -> 按 modelId 请求模型详情
  -> 根据 effort.values 生成推理深度控件
  -> 模型详情加载完成后允许发送聊天
```

### 6.3 usage 流程

```text
AI Service 发起底层模型请求
  -> 将 invocationId 绑定到当前 session 和 turn
  -> 收到供应商 ChatResponse
  -> 读取并规范化 TokenUsage
  -> 更新当前 turn 的最后一次有效 usage
  -> 推送 CONTEXT_USAGE_UPDATED 运行时事件
  -> 助手终态事件保存最后一次有效 usage
  -> 前端使用 usage.totalTokens / model.limit.context 绘制圆环
```

## 7. 模型能力数据源

### 7.1 models.dev 目录

固定请求地址：

```text
https://models.dev/api.json
```

约束：

- 地址硬编码在模型元数据服务中，不写入 `Setting`。
- 每次应用启动只请求一次。
- 请求超时为 10 秒。
- 不自动重试。
- 只缓存在当前进程内。
- 不写磁盘，也不读取上次启动的数据降级。
- 应用运行期间不刷新。

models.dev 根对象按供应商分组，能力位于具体模型对象中：

```text
根对象
└── providerKey
    ├── id
    └── models
        └── modelKey
            ├── id
            ├── name
            ├── family
            ├── status
            ├── limit.context / input / output
            ├── tool_call
            ├── reasoning
            ├── reasoning_options
            ├── attachment
            └── modalities.input / output
```

以下内容不参与匹配，也不进入缓存：

- models.dev 根对象中的 `providerKey`。
- 供应商对象中的 `id`。
- `models` 对象中的 `modelKey`。
- 当前供应商 `/models.data[].owned_by`。

模型的唯一键只使用清洗后的 `model.id`。

### 7.2 当前供应商模型列表

请求地址：

```text
GET {baseUrl}/models
Authorization: Bearer {apiKey}
Accept: application/json
```

约束：

- `api_key` 或 `base_url` 为空时直接终止项目启动。
- 每次应用启动只请求一次。
- 请求超时为 10 秒。
- 不自动重试。
- 响应必须是成功状态，且根对象必须包含 `data` 数组。
- 供应商列表只决定哪些模型可用，不提供本期需要的能力字段。

## 8. 清洗后模型结构

### 8.1 `ModelInfo`

后端使用不可变的 `ModelInfo` 表达清洗后的模型信息：

```text
ModelInfo
├── modelId: String
├── name: String
├── family: String?
├── status: String?
├── limit: ModelLimit
│   ├── context: Long
│   ├── input: Long?
│   └── output: Long
├── toolCall: Boolean
├── reasoning: Boolean
├── reasoningOptions: List<Map<String, Object>>
├── attachment: Boolean
├── inputModalities: List<String>
└── outputModalities: List<String>
```

DTO、model 和嵌套结构实现时均应按项目约定添加 Swagger `@Schema` 注解。

### 8.2 字段规则

| 缓存字段 | models.dev 来源 | 是否可空 | 清洗规则 |
| --- | --- | --- | --- |
| `modelId` | `model.id` | 否 | 必须是非空字符串；去除首尾空白；区分大小写 |
| `name` | `model.name` | 否 | 必须是非空字符串；去除首尾空白 |
| `family` | `model.family` | 是 | 字符串去除首尾空白；空白转为 `null`；不根据 ID 推测 |
| `status` | `model.status` | 是 | 字符串去除首尾空白；空白转为 `null`；保留原值 |
| `limit.context` | `model.limit.context` | 否 | 必须是正整数 |
| `limit.input` | `model.limit.input` | 是 | 缺失时为 `null`；存在时必须是正整数 |
| `limit.output` | `model.limit.output` | 否 | 必须是正整数 |
| `toolCall` | `model.tool_call` | 否 | 缺失或非布尔值时按 `false` |
| `reasoning` | `model.reasoning` | 否 | 缺失或非布尔值时按 `false` |
| `reasoningOptions` | `model.reasoning_options` | 否 | 对象包装成单元素列表；数组只保留对象元素并保持顺序；缺失或类型错误时为空列表 |
| `attachment` | `model.attachment` | 否 | 缺失或非布尔值时按 `false` |
| `inputModalities` | `model.modalities.input` | 否 | 只保留非空字符串，去除首尾空白，按首次出现顺序去重 |
| `outputModalities` | `model.modalities.output` | 否 | 只保留非空字符串，去除首尾空白，按首次出现顺序去重 |

`reasoningOptions` 中的对象保留原始字段和值，包括当前已知的 `type`、`values`、`min` 和 `max`。实现时需要进行只读深拷贝，不能把远端 JSON 可变对象直接暴露给调用方。

### 8.3 有效记录

一条 models.dev 模型记录同时满足以下条件时才有效：

- `model.id` 是非空字符串。
- `model.name` 是非空字符串。
- `model.limit.context` 是正整数。
- `model.limit.output` 是正整数。
- `model.limit.input` 缺失，或者是正整数。

其余字段缺失不影响记录有效性，按字段缺省规则清洗。无效记录跳过并计数，不单独导致启动失败。

### 8.4 状态字段

`alpha`、`beta`、`deprecated` 和未来未知状态都不参与过滤。状态只作为模型详情返回值预留，本期不增加禁用、警告或确认流程。

## 9. 顺序、重复 ID 与匹配

### 9.1 models.dev 重复 ID

必须保持 models.dev 响应的对象遍历顺序：

1. 按根对象中供应商出现顺序遍历。
2. 按供应商 `models` 中模型出现顺序遍历。
3. 无效记录跳过，不占用该 ID。
4. 同一个 `model.id` 只保留第一条有效记录。
5. 后续重复记录不能覆盖已有记录。

实现时使用保持插入顺序的映射，并且只在完整校验通过后执行 `putIfAbsent`。

### 9.2 供应商列表去重

按 `/models.data` 原始顺序处理：

1. 非对象元素跳过。
2. `data[].id` 必须是非空字符串，并去除首尾空白。
3. 供应商列表中的重复 ID 只处理第一次。
4. `owned_by` 和其他字段全部忽略。

如果清洗后没有任何供应商模型 ID，项目启动失败。

### 9.3 模型匹配

按供应商 `/models.data` 原始顺序逐条匹配，使用两阶段规则：

1. 先按 `/models.data[].id == models.dev model.id` 做区分大小写的精确匹配。
2. 精确匹配失败时，分别对供应商 `data[].id` 和 models.dev `model.name` 做模型名归一化后匹配。
3. 归一化结果对应多个元数据模型时视为未匹配，不能默认选择第一条。

模型名归一化规则为：去除首尾空白，使用 `Locale.ROOT` 转为小写，仅保留 Unicode 字母和数字；空格、`-`、`_`、`.`、`/` 等连接符均被忽略。

匹配成功后，最终 `ModelInfo.modelId` 绑定供应商实际模型 ID，保证模型详情、聊天请求、上下文压缩和历史 usage 使用同一个可调用 ID；models.dev 的 `name` 和能力字段仍来自匹配到的元数据记录。

未匹配模型不进入模型列表，也不能通过模型详情接口或聊天接口使用。最终顺序严格跟随供应商 `/models.data`，不使用 models.dev 目录顺序。

最终没有任何匹配模型时，项目启动失败。

## 10. 进程内缓存

启动成功后保存两组不可变数据：

| 缓存 | 类型 | 用途 |
| --- | --- | --- |
| 可用模型 ID 列表 | `List<String>` | 保持供应商顺序，供原模型列表接口返回 |
| 可用模型详情映射 | `Map<String, ModelInfo>` | 按 `modelId` 查询详情和校验聊天请求 |

models.dev 全量清洗映射只在启动匹配阶段使用；匹配完成后可以由模型元数据服务保留，也可以只保留最终可用详情映射，但不能对外查询未匹配模型。

缓存发布后不允许修改。对列表、嵌套列表和 `reasoningOptions` 中的对象都需要做防御性复制。

## 11. 启动失败语义

以下任一情况必须抛出异常并停止 Spring 应用启动：

- `api_key` 为空。
- `base_url` 为空。
- models.dev 请求超时或发生网络异常。
- 供应商 `/models` 请求超时或发生网络异常。
- 任一请求返回非成功 HTTP 状态。
- 任一响应为空。
- 任一响应无法解析为 JSON。
- models.dev 根结构不是对象。
- models.dev 清洗后没有任何有效模型。
- 供应商响应根结构不是对象，或缺少 `data` 数组。
- 供应商 `data` 清洗后没有任何有效模型 ID。
- 最终没有任何匹配模型。

启动异常不能被 `ModelOptionService` 捕获后转换成 `loadErrorMessage`。应让异常沿 Bean 初始化链传播，使应用进程以启动失败结束。

日志要求：

- 使用中文说明失败阶段。
- 网络或 HTTP 错误记录请求地址和状态码。
- 清洗完成记录总记录数、无效记录数、重复 ID 数和最终匹配数。
- 不记录 `api_key`、Authorization 请求头或完整响应正文。
- 单条脏数据只记录必要定位信息，不能输出完整远端对象。

## 12. 后端接口

### 12.1 模型列表

保持现有接口和返回结构：

```http
GET /config/modelList
```

```json
{
  "success": true,
  "data": ["model-a", "model-b"]
}
```

接口返回 `R<List<String>>`。应用只有在缓存初始化成功后才能启动，因此接口不再需要表达启动期模型加载失败。

### 12.2 模型详情

新增接口：

```http
GET /config/modelInfo?modelId={modelId}
```

成功响应示例：

```json
{
  "success": true,
  "data": {
    "modelId": "example-model",
    "name": "Example Model",
    "family": "example",
    "status": null,
    "limit": {
      "context": 1000000,
      "input": 900000,
      "output": 100000
    },
    "toolCall": true,
    "reasoning": true,
    "reasoningOptions": [
      {
        "type": "effort",
        "values": ["low", "medium", "high", "max"]
      }
    ],
    "attachment": false,
    "inputModalities": ["text"],
    "outputModalities": ["text"]
  }
}
```

查询规则：

- `modelId` 去除首尾空白后进行区分大小写的精确查询。
- 只能查询最终匹配缓存中的模型。
- 参数为空或模型不存在时返回统一 `R.failed`，错误文案为“模型不存在或未提供能力信息”。
- HTTP 状态沿用项目现有统一响应约定。

### 12.3 前端代理

保持现有列表代理：

```text
GET /api/model/list -> GET /config/modelList
```

新增动态详情代理：

```text
GET /api/model/{modelId} -> GET /config/modelInfo?modelId={modelId}
```

前后端拼接路径和查询参数时都必须使用 URL 编码，不能直接插入原始模型 ID。

## 13. 聊天请求校验

聊天接口在创建 session、占用 turn 和写入 `USER_MESSAGE` 前完成以下校验：

1. `modelName` 去除首尾空白后不能为空。
2. `modelName` 必须存在于可用模型详情映射中。
3. 空白 `reasoningEffort` 转为 `null`。
4. 非空 `reasoningEffort` 必须是当前模型有效 `effort.values` 中的原始值。
5. 非空 `permissionMode` 必须可反序列化为 `DEFAULT` 或 `FULL_ACCESS`；该字段仅在创建新会话时生效，已有会话不应用。

未知模型错误文案：

```text
模型不存在或未提供能力信息
```

不支持的推理深度错误文案：

```text
当前模型不支持所选思考深度
```

校验失败不能创建空会话、残留 `active_turn_id` 或写入任何 JSONL 事件。

## 14. 推理深度选项

### 14.1 识别规则

第一版只识别 `reasoningOptions` 中满足以下条件的对象：

- `type` 精确等于 `effort`。
- `values` 是数组。
- 数组元素是去除首尾空白后仍非空的字符串。

按 `reasoningOptions` 和 `values` 的原始顺序合并，重复值只保留第一次。空字符串和非字符串值忽略。

`toggle`、`budget_tokens` 和未知类型仍通过详情接口原样返回，但不生成控件，也不能映射为 `reasoningEffort`。

### 14.2 前端选项

存在至少一个有效 `effort.values` 时显示思考深度控件，并始终在最前面增加：

| 显示文本 | 提交值 | 含义 |
| --- | --- | --- |
| `供应商默认` | 空字符串 | 请求不发送 `reasoningEffort`，由供应商选择默认行为 |

目录中的原始值按以下规则翻译：

| 原始值 | 显示文本 |
| --- | --- |
| `default` | 默认 |
| `none` | 关闭 |
| `minimal` | 最低 |
| `low` | 低 |
| `medium` | 中 |
| `high` | 高 |
| `xhigh` | 极高 |
| `max` | 最高 |

未知值直接显示原文。翻译只作用于 UI，聊天请求始终提交目录中的原始值。

空值“供应商默认”和目录值 `default` 是两个不同选项：前者不发送参数，后者向供应商发送字符串 `default`。

### 14.3 切换模型

- 切换模型后立即清除旧模型详情和上下文用量展示状态。
- 新详情加载期间禁用发送按钮和思考深度控件。
- 新模型支持当前本地保存值时可以恢复该值。
- 新模型不支持旧值时重置为“供应商默认”。
- 新模型没有有效 `effort.values` 时不显示思考深度控件，并将 `reasoningEffort` 清空。
- 快速切换模型时使用请求序号或取消控制器忽略迟到详情响应，迟到响应不能覆盖当前模型。
- 详情加载失败时展示就近错误并禁止发送，不能回退到手动输入。

## 15. usage 数据模型

### 15.1 `ContextUsageSnapshot`

```text
ContextUsageSnapshot
├── modelId: String
├── inputTokens: Long?
├── outputTokens: Long?
└── totalTokens: Long
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `modelId` | 本次底层请求实际使用的模型 ID |
| `inputTokens` | 供应商返回的输入 Token 数；缺失时为 `null` |
| `outputTokens` | 供应商返回的输出 Token 数；缺失时为 `null` |
| `totalTokens` | 用于上下文占用展示的实际 Token 总数 |

`ContextUsageSnapshot` 不保存百分比和格式化文本。百分比由前端使用当前模型详情中的 `limit.context` 计算。

### 15.2 规范化规则

每次成功底层模型调用完成后读取 `ChatResponse.tokenUsage()`：

1. `TokenUsage` 为空时，本次 usage 不可用。
2. 负数 Token 字段视为无效。
3. `totalTokenCount` 是非负数时优先作为 `totalTokens`。
4. `totalTokenCount` 缺失时，只有 `inputTokenCount` 和 `outputTokenCount` 都有效才使用两者之和。
5. 无法得到可靠 `totalTokens` 时不生成快照、不推送事件，也不覆盖旧值。

计算式：

```text
totalTokens = usage.totalTokenCount
```

缺失时：

```text
totalTokens = usage.inputTokenCount + usage.outputTokenCount
```

供应商的缓存 Token 通常已包含在输入总数中，推理 Token 通常已包含在输出总数中。本期不额外相加缓存或推理明细，避免重复计数。

### 15.3 当前用量口径

上下文用量表示最后一次成功底层模型调用的占用，不是以下数值：

- 不是整个 session 历史 Token 的累计和。
- 不是整个 turn 内多次工具循环 usage 的累计和。
- 不是计费金额或累计计费 Token。
- 不是下一次请求的 Token 预估。

工具循环产生多次底层模型调用时，后一次有效 usage 覆盖前一次，最终保留最后一次有效值。这个值最接近供应商最后一次实际接收的完整上下文规模。

## 16. usage 采集与关联

### 16.1 监听方式

使用 LangChain4j AI Service 可观测事件，不从前端消息文本推算：

- `AiServiceRequestIssuedEvent`：在底层请求发出前，将 `InvocationContext.invocationId` 绑定到当前 session 和 turn。
- `AiServiceResponseReceivedEvent`：每次底层响应到达时读取 `ChatResponse.tokenUsage()`。

`InvocationContext.chatMemoryId` 当前等于 session ID。监听器通过 session ID 查找 `ActiveTurnRuntime`，并校验：

- 当前 runtime 仍属于相同 session。
- runtime 的 turn 尚未被新 turn 替换。
- `invocationId` 与已绑定调用一致。
- 请求 `modelName` 与当前 turn 使用的模型一致。

校验失败的迟到响应直接忽略，不能覆盖新 turn 或其他模型的用量。

### 16.2 `ModelUsageTracker`

建议增加 `ModelUsageTracker` 统一负责：

- 绑定 AI Service invocation 与当前 `ActiveTurnRuntime`。
- 规范化每次底层响应的 usage。
- 原子更新 runtime 中的最后一次有效 `ContextUsageSnapshot`。
- 通知 runtime 的 usage 事件发送器。
- 记录 usage 缺失或关联失败的必要日志。

请求监听器和响应监听器可以作为两个轻量适配器注册到 `AiServices.registerListeners(...)`，共同委托给 `ModelUsageTracker`。不使用 `ThreadLocal` 关联异步流。

### 16.3 runtime 状态

`ActiveTurnRuntime` 增加：

```text
invocationId
modelId
latestContextUsage
contextUsageEmitter
```

`contextUsageEmitter` 只在当前 SSE 可用时推送运行时事件。SSE 已取消时不能因为推送失败影响模型回调或终态清理。

## 17. SSE 与 JSONL

### 17.1 运行时事件

新增仅通过 SSE 推送的事件类型：

```text
CONTEXT_USAGE_UPDATED
```

Payload：

```json
{
  "messageId": "助手消息 ID",
  "modelId": "example-model",
  "inputTokens": 125000,
  "outputTokens": 1400,
  "totalTokens": 126400
}
```

约束：

- `source` 使用 `SYSTEM`。
- 事件使用当前 session、turn 和助手 `messageId`。
- 每次底层模型响应取得有效 usage 后推送一次。
- 事件不写入 JSONL。
- 相同 turn 的后续事件覆盖前端同一模型的当前用量。

`SessionEventType` 需要将该类型与 `ContextUsageUpdatedPayload` 绑定，并与 `ASSISTANT_MESSAGE_DELTA` 一样标记为运行时事件。`SessionEventStore` 的持久化规则不能仅依赖“除 delta 外都写入”，需要明确维护运行时事件集合。

### 17.2 助手终态快照

`AssistantMessagePayload` 增加可空字段：

```text
contextUsage: ContextUsageSnapshot?
```

生成 `ASSISTANT_MESSAGE` 时读取 runtime 中最后一次有效 usage：

- 正常完成时附加到 `state=complete` 快照。
- 错误或取消前存在非空助手文本时，附加到对应 `state=error/cancel` 快照。
- 本轮没有取得有效 usage 时字段为空，不能写入零值覆盖历史数据。
- 错误或取消且没有助手终态快照时，不额外伪造 `ASSISTANT_MESSAGE`；历史恢复继续使用此前最后一次已持久化用量。

旧 JSONL 没有 `contextUsage` 字段时按无用量兼容。

### 17.3 历史恢复

前端打开会话时：

1. 按现有规则从最后一条有效 `USER_MESSAGE.modelName` 恢复模型。
2. 加载该模型详情。
3. 按 JSONL 顺序找到最后一个 `contextUsage.modelId` 与当前模型相同的助手终态快照。
4. 使用该快照恢复圆环。

历史快照不冻结旧的上下文窗口。恢复时始终使用本次启动加载的当前 `modelInfo.limit.context` 作为分母；远端目录更新后，历史占比允许随当前模型能力变化。

切换到不同模型时立即清空圆环，不使用旧模型的分子搭配新模型的上下文窗口。新模型首次返回有效 usage 后再显示占用。

## 18. 前端上下文用量展示

### 18.1 计算

```text
usageRatio = totalTokens / modelInfo.limit.context
usagePercent = usageRatio * 100
```

前提：

- usage 的 `modelId` 与当前模型一致。
- `totalTokens` 是非负数。
- `limit.context` 是正整数。

任一条件不满足时按无用量处理。

### 18.2 格式化

Token 数统一按十进制 `1000` 转换为 `K`，保留一位小数：

```text
formatTokens(tokens) = (tokens / 1000).toFixed(1) + "K"
```

百分比保留一位小数。完整文案示例：

```text
12.6% · 126.4K / 1000.0K 上下文已使用
```

本期不自动切换为 `M`，保证与参考样式一致。

### 18.3 圆环

- 模型选择器旁常驻显示固定尺寸圆环，不常驻显示文字标签。
- 圆环底轨显示完整窗口，进度弧表示 `usageRatio`。
- 绘制比例限制在 `0%` 到 `100%`，避免超限时图形溢出。
- tooltip 仍显示未截断的真实百分比和 Token 数。
- 本期不根据比例增加警告、危险阈值或自动操作。
- 无有效 usage 时显示灰色空环。

交互：

- 鼠标悬浮圆环时显示完整文案。
- 键盘聚焦时显示同一文案。
- 移动端点击圆环时显示同一文案。
- 无用量时 tooltip 和 `aria-label` 使用“暂无上下文用量数据”。
- 圆环需要稳定宽高，加载、更新和悬浮不能引起模型选择器或输入区位移。

### 18.4 更新规则

- 页面初始加载且历史没有 usage 时显示灰色空环。
- 发起新 turn 时保留上一次成功值，直到收到新的有效 usage。
- 收到 `CONTEXT_USAGE_UPDATED` 后，仅当事件模型与当前模型一致时更新。
- 同一工具循环收到多个事件时使用最后到达且关联有效的事件。
- 本次响应缺少 usage 时保留已有值。
- 模型切换时立即清空，不沿用旧模型值。

## 19. 前端模型状态

建议将当前字符串模型状态扩展为：

```text
modelOptions: string[]
selectedModelId: string
selectedModelInfo: ModelInfo | null
modelInfoState: idle | loading | ready | error
reasoningEffort: string
contextUsage: ContextUsageSnapshot | null
```

初始化规则：

1. 加载模型 ID 列表。
2. 本地保存的模型仍在列表中时恢复，否则选择第一项。
3. 不再进入手动模型模式，不再渲染手动输入框。
4. 请求所选模型详情。
5. 详情成功后校验本地推理深度并允许发送。

发送按钮在以下情况禁用：

- 模型列表尚未加载。
- 没有可选模型。
- 模型详情正在加载或加载失败。
- 所选 `reasoningEffort` 不在当前模型允许值中。
- 现有聊天流程定义的其他禁用条件成立。

## 20. 组件职责

### 20.1 `ModelMetadataService`

- 请求一次固定 models.dev 地址。
- 校验根结构。
- 按原始顺序清洗记录。
- 实现首条有效重复 ID 规则。
- 返回不可变的全量清洗映射。
- 请求、解析或全局清洗失败时抛出启动异常。

### 20.2 `ModelOptionService`

- 校验模型服务配置。
- 请求一次当前供应商 `/models`。
- 清洗供应商模型 ID 并按原始顺序去重。
- 与 models.dev 清洗目录精确匹配。
- 发布可用模型 ID 列表和详情映射。
- 提供 `requireModelInfo(modelId)` 供详情和聊天校验复用。
- 任一初始化失败或最终无匹配模型时抛出启动异常。

### 20.3 `ConfigController`

- 保持 `/config/modelList` 返回 `R<List<String>>`。
- 新增 `/config/modelInfo` 返回完整模型详情。
- 不提供 models.dev 全量目录查询接口。

### 20.4 `ModelUsageTracker`

- 监听每次底层 AI Service 请求和响应。
- 关联 invocation、session、turn 和模型。
- 规范化 `TokenUsage`。
- 更新 runtime 并触发 usage SSE。
- 忽略缺失、无效和迟到 usage。

### 20.5 `TurnService`

- 启动模型前校验可用模型和推理深度。
- 为 runtime 绑定模型 ID、助手消息 ID 和 usage 发送器。
- 将最后一次有效 usage 写入助手终态 Payload。
- 终态和取消时清理 usage 关联状态。

### 20.6 前端页面

- 删除手动模型输入和相关回退状态。
- 模型切换时请求详情并处理竞态。
- 根据 `effort.values` 构造翻译后的控件。
- 处理运行时 usage 事件和历史 usage 恢复。
- 渲染圆环及可访问 tooltip。

## 21. 失败处理

| 场景 | 行为 |
| --- | --- |
| 启动配置缺失 | 抛出启动异常，停止项目启动 |
| models.dev 请求或解析失败 | 抛出启动异常，停止项目启动 |
| 供应商 `/models` 请求或解析失败 | 抛出启动异常，停止项目启动 |
| models.dev 存在局部无效记录 | 跳过并统计；全局仍有有效记录时继续 |
| 供应商存在局部无效 ID | 跳过；最终仍有有效匹配时继续 |
| 最终没有匹配模型 | 抛出启动异常，停止项目启动 |
| 模型详情查询未知 ID | 返回统一失败响应 |
| 聊天提交未知 ID | 在创建 turn 前拒绝 |
| 推理深度不受支持 | 在创建 turn 前拒绝 |
| 模型详情前端加载失败 | 显示错误并禁用发送，不提供手动回退 |
| usage 缺失或无效 | 不更新、不伪造，保留已有有效值 |
| usage 迟到或 invocation 不匹配 | 忽略，不影响当前 turn |

## 22. 安全与一致性

- 远端地址固定使用 HTTPS。
- 供应商 Authorization 只发送给当前 `base_url`，不能发送给 models.dev。
- 日志不能输出密钥、Authorization 或完整远端响应。
- 所有模型 ID 比较都区分大小写，且在进入缓存和查询前只做首尾空白清理。
- 模型列表、模型详情和聊天校验必须读取同一份最终匹配缓存。
- 前端详情响应、usage 事件和历史 usage 都必须按 `modelId` 校验，不能把不同模型的数据混合。
- usage 监听异常不能中断模型主流程；关联或解析失败只记录必要日志。

## 24. 验收标准

- 应用每次启动只请求一次 models.dev 目录和一次供应商 `/models`，两次请求均为 10 秒超时且不重试。
- 缺少模型服务配置、任一请求或解析失败、全局无有效目录记录或最终无匹配模型时，Spring 启动失败。
- models.dev 重复 ID 保留原始顺序中的第一条有效记录。
- 模型匹配先使用 `model.id` 与 `/models.data[].id` 精确匹配，失败后使用归一化的供应商 ID 与元数据 `name` 匹配；归一化冲突视为未匹配。
- `/config/modelList` 继续返回按供应商顺序排列的 `List<String>`。
- 模型详情接口只返回成功匹配模型的全部清洗字段。
- 前端不再提供手动模型输入，聊天接口也拒绝未知模型。
- 推理控件只根据 `effort.values` 生成，显示中文标签但提交原始值，并保留“供应商默认”空选项。
- `toggle`、`budget_tokens`、`toolCall`、附件和模态只作为预留信息，不改变本期行为。
- 工具循环中每个成功底层响应的有效 usage 都能通过 SSE 更新圆环，后一次覆盖前一次。
- 用量分子使用供应商 `totalTokenCount`，缺失时才使用有效的输入与输出之和，不重复增加缓存或推理子项。
- 助手终态保存最后一次有效 usage，旧 JSONL 缺失该字段时可正常回放。
- 模型切换后旧 usage 立即清空，只有模型 ID 一致的详情和 usage 能更新当前界面。
- 页面常驻显示圆环，悬浮、聚焦或移动端点击时显示类似 `12.6% · 126.4K / 1000.0K 上下文已使用` 的文案。

## 26. 上下文窗口自定义补充

上下文窗口自定义能力以[《上下文窗口自定义设计》](./上下文窗口自定义设计.md)为准，并补充以下口径：

- `ModelInfo.limit.context` 始终是 models.dev 提供的模型能力上限，不能被用户偏好覆盖。
- 用户偏好按供应商实际模型 ID 保存，生效值为 `effectiveContextLimit`。
- 圆环分母使用 `effectiveContextLimit`；没有 usage 时提示当前生效上限。
- 自定义下限为十进制 `100K`，模型能力低于 `100K` 时只读展示。
- 自定义值不设置或缩小主模型 `maxOutputTokens`。
- 点击圆环打开上下文窗口调节面板，保存最大值或恢复默认会删除偏好记录。
